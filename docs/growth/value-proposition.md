# ProfitCtl Value Proposition

`ProfitCtl` helps AI-native software teams compare architecture, model, API, pricing, and contract choices before they ship them.

## One-Line Positioning

> ProfitCtl is unit economics as code for AI-native software teams.

Expanded:

> ProfitCtl models pricing, unit economics, AI/tool costs, and recurring-margin risk so agents and developers can compare decisions before spend becomes real.

## Who It Is For

Start with teams that already have a real cost-sensitive decision in motion:

- AI SaaS teams choosing hosting, database, search, model, or agent runtime patterns
- agent builders adding paid APIs, deep research, model routing, or tool calls
- devtools founders deciding whether a feature is worth its variable cost
- B2B SaaS founders choosing between tiered, mix, or hybrid pricing
- product and finance leads checking recurring margin before packaging changes
- RevOps, sales, or CS teams defending pilot-heavy contracts
- teams that can share a small set of real inputs for calibration

## Who It Is Not For

Do not lead with ProfitCtl for users who want:

- generic personal finance planning
- a hosted collaboration suite first
- a billing system of record
- a vague simulator without a decision to make
- an invoice-grade provider-pricing oracle without telemetry or billing inputs

## What To Say

Use this language in demos, intros, and outbound:

- "Compare one pricing shape against one realistic alternative before you commit."
- "Compare one architecture or AI API decision against one realistic alternative before you ship."
- "See recurring margin and operating cost per user before you sign."
- "Make agent recommendations cite ProfitCtl assumptions, margins, p95 stress, and covenants."
- "Use the output to decide whether a contract is safe to ship."

## What The User Gets

The first useful product motion is simple:

1. install `profitctl`
2. run one `compare` or cost-aware agent workflow
3. review recurring margin, p95 margin, operating cost per user, and covenant health
4. calibrate the model with their real inputs
5. decide whether to change the architecture, AI tool, pricing, or contract shape

## Call-To-Action Path

When someone shows interest, send them through the same path every time:

1. install with the public release or Bun package
2. open one benchmark pair or agent demo that matches their problem
3. run `profitctl compare` or the ProfitCtl cost-aware skill helper
4. capture the minimum inputs needed to calibrate
5. agree on a follow-up if the result is decision-relevant

## Short Proof Statement

If the product is working, the evaluator should be able to answer this quickly:

> Which pricing or contract shape is easier to defend in steady state, and why?

For the agent wedge:

> Which architecture, AI API, or model-routing choice keeps the product inside margin targets, and why?
